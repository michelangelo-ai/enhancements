# RFC-20260930-agentjob: AgentJob — a Michelangelo CRD for Sandboxed, Run-to-Completion Agent Execution

- **Status:** Draft
- **Author(s):** @NolanFoster
- **Created:** 2026-09-30
- **Internal ERD:** (internal, not linked here)

---

## Problem statement

Michelangelo has first-class workload CRDs for batch/ML compute (`Job`, `RayJob`, `SparkJob` in `proto/api/v2`). Each schedules a well-defined, trusted workload with a known resource shape and a fixed entrypoint, launched (in the common case) from a Uniflow-compiled `PipelineRun` workflow via a worker activity (`go/worker/activities/*`) that calls the CRD's gRPC service.

None of these fit a growing class of workload: an **autonomous agent harness** that runs arbitrary, often LLM-generated, code or shell commands to completion inside a single execution (for example, an agent that plans, writes, and runs code to answer a task, then exits). This workload differs from existing job types in ways that matter for both its API shape and its security model:

1. **Untrusted / semi-trusted execution.** The code path executed is not fully known ahead of time, so it needs strong isolation (syscall filtering, no host network by default, no persistent state) beyond what a normal `batch/v1.Job` pod or a `RayJob` worker pod gets.
2. **Single-run semantics with a richer failure taxonomy.** An agent run is not a long-lived service and not a retryable batch step — it runs once, to a terminal state, similar in spirit to how a `RayJob` reaches `SUCCEEDED`/`FAILED`. But "the sandbox never came up" and "the agent's own generated code failed" are qualitatively different events that existing job CRDs' binary succeeded/failed status cannot distinguish — and that distinction is exactly the debugging signal users of a sandboxed-execution CRD most need.
3. **A payload, not a script reference — and a structured result, not just a log stream to scrape.**

Today, teams that need this either bypass Michelangelo entirely (hand-rolled Kubernetes Jobs with no scheduling, resource-pool, or observability integration) or overload an existing CRD.

We propose **`AgentJob`**, a new Michelangelo CRD purpose-built for this workload, whose execution isolation is delegated to [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox) rather than reimplemented.

### Scope boundary: why a standalone CRD, not a pipeline-task plugin

Michelangelo already has a lighter-weight pattern for adding a new compute backend to a pipeline: a Uniflow task plugin that owns its resource directly within a `PipelineRun`'s workflow (the `RayTask`-style pattern), without a dedicated top-level CRD. We considered this for `AgentJob` and rejected it (see [Alternative D](#alternative-d-model-agentjob-as-a-uniflow-pipeline-task-plugin-à-la-raytask)) because agent-harness runs are frequently submitted and polled independently of any pipeline — by an external caller, a CLI, or a service — and need their own get/apply/delete/list lifecycle, RBAC, and audit trail, the same way `RayJob` does. A task-plugin model would make `AgentJob` invisible outside the pipeline that launched it.

## Motivation

- **First-class citizenship.** Give agent-harness workloads the same treatment as `RayJob`/`SparkJob`: submission via the Michelangelo API, phase/status tracking, resource-pool-aware scheduling, and consistent RBAC/audit through `UserInfo`.
- **Avoid reinventing pod-level isolation.** `kubernetes-sigs/agent-sandbox` already provides `Sandbox` / `SandboxClaim` / `SandboxWarmPool` primitives with gVisor-based isolation (Kata/Firecracker also supported via `RuntimeClass`) — exactly the isolation properties an agent-harness workload needs. None of the OSS job-CRD projects we surveyed reimplement this kind of isolation once a dedicated isolation primitive exists; `AgentJob` should consume agent-sandbox, not duplicate it.
- **Reuse existing vocabulary.** Reuse Michelangelo's already-public scheduling/placement types (`Affinity`, `SchedulingSpec`, `AssignmentInfo`, `SchedulingInfo` in `proto/api/v2/job.proto`) instead of introducing a parallel set of agent-specific concepts.
- **A better status model.** Give `AgentJob` a 3-way terminal split and a machine-readable failure reason, rather than the coarser 2-way success/fail that `RayJob`/`SparkJob` use today. Run-to-completion job systems have converged on this (Argo's `Failed` vs. `Error`, KubeRay's `JobFailedReason`, Flyte's distinct `Aborted`), and it matters even more here because "sandbox never provisioned", "agent code exited non-zero", and "we killed it" call for fundamentally different operator actions.

## Goals

- Define an `AgentJob` CRD (`proto/api/v2/agent_job.proto`) with `AgentJobSpec` / `AgentJobStatus` / `AgentJobPhase`, following the same structural conventions as `RayJob`/`SparkJob` (TypeMeta/ObjectMeta/Spec/Status, Condition-based sub-status, explicit `_INVALID = 0` enum defaults).
- Specify how the `AgentJob` controller creates and manages an underlying agent-sandbox `Sandbox`/`SandboxClaim` as the execution primitive for a single run, reacting to its status via **watches** (`Owns()`/`Watches()`), not polling. This explicitly avoids the `RayJob` controller's known gap (`go/components/ray/job/controller.go`, tracked as `TODO(#605)`) of polling a foreign CRD's status on a flat interval — unnecessary here since `Sandbox`/`SandboxClaim` live in the same cluster (unlike Ray's federated remote-cluster jobs).
- **Guarantee cleanup** of the `Sandbox`/`SandboxClaim` on `AgentJob` deletion. A leaked sandbox is leaked, potentially security-sensitive compute; `AgentJob` must close this gap rather than inherit it.
- Support passing a run-specific **payload** to the sandboxed execution, and produce a **structured result** (exit code, bounded output, optional artifacts) rather than requiring consumers to scrape logs.
- Distinguish **infra-level** failure (sandbox never provisioned) from **agent-level** failure (harness ran but the agent's task failed) via a phase/reason model.
- Model retries as **always claiming a fresh `Sandbox`/`SandboxClaim`**, never re-entering one that already ran semi-trusted code — a security requirement, not just hygiene.
- Reuse existing Michelangelo API types (`UserInfo`, `Affinity`, `SchedulingSpec`, `ClusterSpec`, `AssignmentInfo`, `SchedulingInfo`) wherever their semantics already match.
- Define a minimal, generic `AgentJobResources` shape (CPU / memory / GPU requests) independent of any one caller's runtime.

## Non-goals

- **Re-implementing or extending `kubernetes-sigs/agent-sandbox` itself.** Its `Sandbox`, `SandboxClaim`, `SandboxWarmPool`, and isolation model are treated as an external dependency. Hardening/operating guidance for that project is being pursued separately as an upstream proposal and is out of scope here.
- **Multi-step or long-running agent orchestration** (planning graphs, multi-turn conversations across separate runs). `AgentJob` models exactly one bounded execution, analogous to a single `RayJob`/`SparkJob` run. Composing multiple `AgentJob`s is left to existing Michelangelo pipeline tooling; a `go/worker/activities/agent` + `workflows/agent` pair can invoke `AgentJob` from a Uniflow pipeline the same way `RayJob`/`SparkJob` are invoked today, but that pair is not part of this proposal.
- **A general-purpose "run arbitrary container" API.** `AgentJob` is scoped to the agent-harness use case (payload in, isolated execution, structured result out), not a replacement for `batch/v1.Job` or `RayJob`.
- **Autoscaling or fleet-wide warm-pool sizing policy** for the underlying sandbox pool — deferred to whatever guidance agent-sandbox itself provides for `SandboxWarmPool` sizing.
- **`run` / `logs` / `watch` CLI verbs** beyond the standard get/apply/delete — called out explicitly in [Open questions](#open-questions) rather than silently inheriting `RayJob`/`SparkJob`'s current gap, but not blocking this proposal.

## High-level architecture

```
                     +---------------------------+
   AgentJob (CRD) -->|  go/components/agentjob   |
   (this proposal)   |  controller               |
                     +-------------+-------------+
                                   |
                                   | Owns()/Watches() (same-cluster,
                                   | not polled — see Goals)
                                   v
                     +---------------------------+
                     |  Sandbox / SandboxClaim   |  <- kubernetes-sigs/agent-sandbox
                     |  (gVisor-isolated pod)    |     (external dependency, unmodified;
                     +-------------+-------------+      vendored/pinned Go API types)
                                   |
                                   | exec: run harness with payload
                                   v
                     +---------------------------+
                     |  Agent harness process    |
                     |  (image from spec)        |
                     +---------------------------+
```

1. **Controller registration.** The `AgentJob` controller is a new package, `go/components/agentjob/{job,module.go}`, registered onto the shared controller-runtime `Manager` via `fx.Invoke(register)` exactly like `go/components/ray/job/module.go` — not a fork of agent-sandbox's own controller.
2. **Scheduling and placement.** On creation, the controller resolves placement (`Affinity`, `ClusterSpec`) via the existing `jobs/scheduler` (Kueue) + `jobs/cluster` + `jobs/client` federation layer, extending `jobs/compute.Factory` with an "agent sandbox" backend — the same extension point `RayJob`/`SparkJob` already use for their compute engines.
3. **Sandbox provisioning.** The controller creates a `Sandbox` (or claims one from a `SandboxWarmPool` via `SandboxClaim`), `Owns()`/`Watches()` it so status changes trigger immediate reconciles, and invokes the sandbox's exec API to start the agent harness with the run's payload.
4. **Cleanup contract (explicit, not implicit).** The controller either:
   - **(a)** sets a Kubernetes owner reference from the `Sandbox`/`SandboxClaim` to the `AgentJob` so garbage collection deletes it automatically, or
   - **(b)** places an explicit finalizer on the `AgentJob` that deletes the `Sandbox`/`SandboxClaim` before allowing the `AgentJob` itself to be removed.

   This RFC proposes **(a)** as the default (simpler; matches how most Kubernetes controllers manage owned resources), with **(b)** as a fallback if agent-sandbox resources don't cleanly support owner references from a foreign API group — see [Open questions](#open-questions).
5. **Terminal state.** On success, failure, infra error, or an explicit kill request, the controller tears down the sandbox and records status. Used sandboxes are **never** returned to a warm pool, per the "never reuse a sandbox that ran untrusted code" requirement. The `AgentJob` then follows the same lifecycle every other terminal Michelangelo CRD uses: mark immutable → ingester archives to MySQL → CR deleted from etcd.

### Phase transitions

```
PENDING ──> PROVISIONING ──> RUNNING ──> SUCCEEDED
                 │              │
                 │              └──────> FAILED     (agent-level: non-zero exit, timeout, OOM, policy violation)
                 └─────────────────────> ERRORED    (infra-level: provision failure, claim timeout, eviction)

any non-terminal ──(kill request)──> KILLING ──> KILLED
```

### Runtime variants

Two integration patterns are anticipated:

1. **Harness runs inside the sandbox.** The sandbox image bundles the agent harness; the controller execs a single command and waits for exit. Simpler, and maps directly onto agent-sandbox's existing exec-and-wait pattern.
2. **External harness drives the sandbox.** The controller (or a controller-managed sidecar) treats the sandbox purely as an isolated execution surface and drives it step-by-step through its exec API. More flexible, more moving parts.

This RFC proposes starting with **variant 1** and leaves variant 2 as a documented future extension point.

## APIs and CRDs

New file `proto/api/v2/agent_job.proto`, following the existing `spark_job.proto` / `ray_job.proto` layout and conventions (TypeMeta/ObjectMeta embedding, `option (michelangelo.api.resource) = { conversion: true };`, `option (michelangelo.api.resource_list) = {};`, explicit `_INVALID = 0` enum defaults, and field-level doc comments as the documentation source of truth):

```protobuf
syntax = "proto3";

package michelangelo.api.v2;

option go_package = "v2";

import "google/protobuf/struct.proto";
import "k8s.io/apimachinery/pkg/apis/meta/v1/generated.proto";
import "michelangelo/api/options.proto";
import "michelangelo/api/conditions.proto";
import "michelangelo/api/v2/job.proto";
import "michelangelo/api/v2/user.proto";
import "michelangelo/api/v2/cluster.proto";

// AgentJobPhase enumerates the lifecycle states of an AgentJob run.
// Distinguishes infra-level outcomes (sandbox never came up, killed by us)
// from agent-level outcomes (harness ran, agent's own task succeeded/failed),
// per the 3-way terminal split used by Argo Workflows (Succeeded/Failed/Error)
// and RayJob's infra/app status split.
enum AgentJobPhase {
  AGENT_JOB_PHASE_INVALID = 0;
  AGENT_JOB_PHASE_PENDING = 1;       // not yet scheduled
  AGENT_JOB_PHASE_PROVISIONING = 2;  // Sandbox/SandboxClaim requested, not yet ready
  AGENT_JOB_PHASE_RUNNING = 3;       // sandbox ready, harness executing
  AGENT_JOB_PHASE_SUCCEEDED = 4;     // agent's own task completed successfully
  AGENT_JOB_PHASE_FAILED = 5;        // harness ran; agent's task failed (non-zero exit, policy violation)
  AGENT_JOB_PHASE_ERRORED = 6;       // infra-level failure: sandbox never provisioned, node eviction, etc.
  AGENT_JOB_PHASE_KILLING = 7;       // termination requested, sandbox teardown in progress
  AGENT_JOB_PHASE_KILLED = 8;
}

// Machine-readable reason accompanying a terminal AgentJobPhase, analogous to
// RayJob's JobFailedReason. `message` (see AgentJobStatus) remains the
// free-text human-readable string; `reason` is the stable, matchable enum.
enum AgentJobFailureReason {
  AGENT_JOB_FAILURE_REASON_INVALID = 0;
  AGENT_JOB_FAILURE_REASON_SANDBOX_PROVISION_FAILED = 1;
  AGENT_JOB_FAILURE_REASON_SANDBOX_CLAIM_TIMEOUT = 2;
  AGENT_JOB_FAILURE_REASON_AGENT_TIMEOUT = 3;
  AGENT_JOB_FAILURE_REASON_AGENT_NON_ZERO_EXIT = 4;
  AGENT_JOB_FAILURE_REASON_AGENT_POLICY_VIOLATION = 5;
  AGENT_JOB_FAILURE_REASON_AGENT_OOM_KILLED = 6;
}

// Reference to the agent definition/harness image to execute.
message AgentDefinitionRef {
  // Container image reference for the agent harness.
  string image = 1;
}

// Resource requests for the sandboxed execution.
message AgentJobResources {
  string cpu = 1;
  string memory = 2;
  // Optional GPU resource name (e.g. "nvidia.com/gpu") and count.
  string gpu_type = 3;
  int32 gpu_count = 4;
}

// Structured result of a completed run, avoiding the need to scrape sandbox
// logs for the answer (cf. Argo's NodeStatus.Outputs.Result pattern).
message AgentJobResult {
  int32 exit_code = 1;
  // Bounded, truncated summary of the harness's own reported output.
  string output = 2;
  // Opaque, caller-defined structured result payload.
  google.protobuf.Struct artifacts = 3;
}

message AgentJobSpec {
  // User initiating the agent run.
  UserInfo user = 1 [(michelangelo.api.validation) = {required: true}];

  // Placement/resource-selection rules — reused as-is from job.proto.
  Affinity affinity = 2;

  // Preemption/scheduling behavior — reused as-is from job.proto.
  SchedulingSpec scheduling = 3;

  // Target cluster for the underlying sandbox.
  ClusterSpec cluster = 4;

  // Caller-supplied identifier correlating this run to an external system.
  // Opaque to Michelangelo; not interpreted or validated beyond length/charset.
  string run_id = 5 [(michelangelo.api.validation) = {
    required: true, max_length: "256", pattern: "^[A-Za-z0-9._:-]+$"
  }];

  // Agent harness image to run inside the sandbox.
  AgentDefinitionRef agent_definition = 6;

  // Run-specific input payload passed to the harness. Marked sensitive since
  // this may carry caller-provided task input.
  google.protobuf.Struct payload = 7 [(michelangelo.api.sensitive) = true];

  // Resource requests for the sandbox.
  AgentJobResources resources = 8;

  // Deadline for the underlying Sandbox/SandboxClaim to become ready, bounding
  // provisioning time (cold pod / cold microVM boot, warm-pool exhaustion)
  // separately from total run time — mirrors RayJob's preRunningDeadlineSeconds.
  int32 sandbox_ready_deadline_seconds = 9;

  // Deadline for the whole run (provisioning + execution) — mirrors k8s Job's
  // and RayJob's activeDeadlineSeconds.
  int32 active_deadline_seconds = 10;

  // How long to retain a terminal AgentJob record before cleanup. Callers may
  // want a shorter TTL for Failed/Errored runs than Succeeded ones, given a
  // failed sandbox may hold less-trustworthy artifacts/state.
  int32 ttl_seconds_after_finished = 11;
}

message AgentJobStatus {
  AgentJobPhase phase = 1;

  // Machine-readable failure reason, set when phase is FAILED or ERRORED.
  AgentJobFailureReason failure_reason = 2;

  // Human-readable status message.
  string message = 3;

  // Where the run was placed.
  AssignmentInfo assignment = 4;

  // Scheduling attempt history.
  SchedulingInfo scheduling_info = 5;

  // Name/UID of the underlying Sandbox/SandboxClaim object, for debugging.
  // AgentJob's own phase is authoritative; this is a disposable implementation
  // detail, not a second source of truth for terminal state.
  string sandbox_ref = 6;

  // Structured result, populated once the harness reports a result.
  AgentJobResult result = 7;

  repeated Condition status_conditions = 8;
}

message AgentJob {
  option (michelangelo.api.resource) = { conversion: true };

  k8s.io.apimachinery.pkg.apis.meta.v1.TypeMeta type_meta = 1;
  k8s.io.apimachinery.pkg.apis.meta.v1.ObjectMeta metadata = 2;

  AgentJobSpec spec = 3;
  AgentJobStatus status = 4;
}

message AgentJobList {
  option (michelangelo.api.resource_list) = {};

  k8s.io.apimachinery.pkg.apis.meta.v1.TypeMeta type_meta = 1;
  k8s.io.apimachinery.pkg.apis.meta.v1.ListMeta metadata = 2;

  repeated AgentJob items = 3;
}
```

Example resource:

```yaml
apiVersion: michelangelo.api/v2
kind: AgentJob
metadata:
  name: summarize-report-7f3c
  namespace: team-agents
spec:
  user:
    name: alice
  runId: "ext-system:run-12345"
  agentDefinition:
    image: registry.example.com/agents/code-harness:1.4.0
  payload:
    task: "Summarize the attached CSV and plot weekly totals."
  resources:
    cpu: "2"
    memory: 4Gi
  sandboxReadyDeadlineSeconds: 120
  activeDeadlineSeconds: 1800
  ttlSecondsAfterFinished: 3600
```

### Reuse vs. new fields

`TerminationSpec` / `TerminationType` (`job.proto`) are deliberately **not** reused for terminal reporting: their 2-value `SUCCEEDED`/`FAILED` enum can't represent the infra/agent failure distinction this RFC treats as a core goal. `AgentJobPhase` and `AgentJobFailureReason` exist specifically to carry that extra granularity. `Affinity`, `SchedulingSpec`, `AssignmentInfo`, `SchedulingInfo`, `UserInfo`, and `ClusterSpec` are reused verbatim.

### Service

The CRUD/List service (`agent_job_svc.proto`) is generated, not hand-authored, via `tools/grpc-svc-gen.sh AgentJob`, following the same pattern as every other Michelangelo resource.

### Foreign-CRD reference gap

Michelangelo's existing `(michelangelo.api.resource_reference)` proto annotation (used, e.g., by `SparkJobSpec`'s cluster reference) only supports referencing another Michelangelo-native CRD by its `michelangelo.uber.com/<Kind>` type string. There is no annotation for referencing a foreign CRD such as agent-sandbox's `Sandbox`/`SandboxClaim`. This RFC proposes `sandbox_ref` as a plain string field with no cross-reference validation for the initial version, and flags a foreign-reference annotation as an open question rather than a blocking requirement.

## Alternatives considered

### Alternative A: Plain `batch/v1.Job`, no `AgentJob` CRD, no sandbox integration

**Pros:** Zero new API surface; teams already do this today by hand.
**Cons:** No Michelangelo scheduling integration (resource pools, `Affinity`, RBAC via `UserInfo`), no consistent phase/status model, and — most importantly — no strong isolation guarantee.
**Why not chosen:** Leaves the isolation problem this RFC exists to solve entirely unsolved.

### Alternative B: Extend `Job` (the generic Michelangelo job CRD) with an "agent mode"

**Pros:** No new CRD to register and maintain.
**Cons:** `Job`'s semantics aren't built around a payload-driven, single-shot, sandbox-backed execution model with a richer failure taxonomy. Overloading it would require enough new optional fields that the result is effectively a new CRD anyway, without a clean name.
**Why not chosen:** Michelangelo's own precedent — `RayJob` and `SparkJob` were split out from generic `Job` rather than folded into it — favors a dedicated CRD per compute engine.

### Alternative C: Reimplement pod-level isolation instead of depending on agent-sandbox

**Pros:** No external dependency to track or vendor.
**Cons:** Duplicates real, already-solved isolation engineering (gVisor `RuntimeClass` setup, warm-pool management, exec API) that agent-sandbox maintains upstream.
**Why not chosen:** None of the surveyed projects (Argo, Flyte, KubeRay) reimplement sandboxing once a dedicated isolation primitive exists in the ecosystem; depending on agent-sandbox is the point.

### Alternative D: Model AgentJob as a Uniflow pipeline-task plugin (à la `RayTask`)

**Pros:** Matches Michelangelo's lighter-weight "task owns the resource" pattern; avoids a new top-level CRD, gRPC service, RBAC surface, and CRD versioning/backward-compatibility obligations under `go/api/crd/sync.go`.
**Cons:** Makes `AgentJob` invisible and unmanageable outside the pipeline that launched it — no independent get/list, no direct submission by a non-pipeline caller, no standalone audit trail.
**Why not chosen:** Agent-harness runs are expected to be submitted and polled independently at least as often as `RayJob`/`SparkJob`. Job CRDs are typically launched by a workflow activity but still exist as independently addressable resources, so the heavier CRD route is justified. A future `go/worker/activities/agent` + `workflows/agent` pair (see [Non-goals](#non-goals)) can still let a pipeline launch an `AgentJob` the same way it launches a `RayJob` today.

## Open questions

- [ ] **Owner references vs. finalizer for cleanup.** Does agent-sandbox cleanly support Kubernetes owner references from a foreign API group (Michelangelo's `AgentJob`), or does this need an explicit finalizer-driven delete? This is safety-critical and must be resolved before implementation, not deferred.
- [ ] **`Sandbox` vs. `SandboxClaim` pooling model.** Does agent-sandbox's `Sandbox`/`SandboxClaim` distinction map 1:1 onto one-sandbox-per-`AgentJob`, or is there a claim-reuse/pooling model that complicates the ownership and deletion story above?
- [ ] **Foreign-CRD reference annotation.** Should `michelangelo/api/options.proto` gain a `(michelangelo.api.foreign_resource_reference)`-style annotation for non-Michelangelo CRDs like `Sandbox`, or is an unvalidated string (as proposed for `sandbox_ref`) acceptable for v1?
- [ ] **CI-gated integration/e2e test.** The repo has no codified Go e2e target for controllers managing a foreign CRD (existing sandbox integration tests are a manually-invoked `poetry run ma sandbox create` step). A concrete scenario — submit `AgentJob` → `Sandbox`/`SandboxClaim` created → harness runs → terminal phase observed → resources GC'd — and its CI target name should be agreed before implementation begins.
- [ ] **Single- vs. multi-version CRD at launch.** `go/api/crd/sync.go`'s `SyncCRDs` rejects backward-incompatible schema changes once a CRD has live instances. Should `AgentJob` launch single-version and defer multi-version support until the schema stabilizes?
- [ ] **Vendored agent-sandbox API version.** Which module path/version of agent-sandbox's Go API types should be vendored and pinned (mirroring how `github.com/ray-project/kuberay/ray-operator/apis/ray/v1` is vendored today), given agent-sandbox is an early-stage SIG project without a long-term API stability guarantee?
- [ ] **CLI/SDK verbs beyond get/apply/delete.** Should `AgentJob` ship `logs`/`watch`/`run` verbs at launch? `RayJob`/`SparkJob` lack them today, but sandboxed run-to-completion workloads are exactly where users most want to tail output and debug failures.
- [ ] **Payload size cap.** Should `payload` have a size limit enforced at the API layer, given it is stored inline as a `google.protobuf.Struct` rather than as a reference to external storage?
- [ ] **Runtime variant 2.** Is there a near-term consumer for the "external harness drives the sandbox" variant that would justify designing for it in v1, or is it safe to defer?

## Rollout strategy

### Phase 1 — Alpha: API surface only

- Add `agent_job.proto`; generate `agent_job_svc.proto` via `tools/grpc-svc-gen.sh AgentJob`.
- Add both to `proto/api/v2/BUILD.bazel`'s `v2_proto.srcs`, run `tools/gazelle`, `bazel build //proto/...`, then `tools/gen-proto-go.sh` to sync `proto-go/`.
- Launch as a single-version CRD (pending the open question above) to avoid `crd.SyncCRDs`'s backward-incompatible-change rejection during early iteration.

### Phase 2 — Alpha: controller behind a feature flag

- **Registration** mirrors `go/components/ray/job/module.go`: `NewReconciler(...)` constructor, `Register(mgr) error`, wired via `fx.Invoke(register)`.
- **Watch strategy:** `.For(&v2pb.AgentJob{}).Owns(&sandboxv1.Sandbox{})` — explicitly not the poll-based approach `RayJob` uses for its federated remote-cluster jobs.
- **RBAC:** add the `ClusterRole` diff (`helm/michelangelo/templates/rbac/clusterrole.yaml`) for agent-sandbox's API group and resources (`sandboxes`, `sandboxclaims`, and their `/status` subresources) in the same PR as the controller — this YAML is hand-maintained and easy to omit.
- **Backoff:** differentiated requeue/backoff for provisioning vs. running states rather than a single flat interval, given sandbox cold-start latency variance.
- **Runtime:** variant 1 (harness inside sandbox) only.
- Ship as one closed loop: proto + generated service proto + Bazel wiring; generated `proto-go/` sources; RBAC diff; fx module wiring; table-driven unit tests (fake client + gomock, covering every reconcile branch, mirroring `go/components/ray/job/controller_test.go`); and the CI-gated integration test agreed in Open questions.

### Phase 3 — Beta

- Validate against a single sandbox cluster, then enable across all `ClusterSpec` targets.
- Add a `go/worker/activities/agent` + `workflows/agent` pair if pipeline-launched usage materializes.
- Revisit CLI verbs and runtime variant 2 based on alpha feedback.

### Phase 4 — GA

- Remove the feature flag once the CRD schema is stable and multi-version support (if needed) is in place.
- Exact release milestones to be mapped with the assigned Shepherd.

### Migration and rollback

- **Migration:** none needed — this is wholly new API surface with no prior resource to migrate from.
- **Rollback:** disable the controller feature flag. Because sandboxes are owned by (or finalized through) their `AgentJob`, deleting outstanding `AgentJob` resources tears down any associated sandboxes; the CRD can then be removed without affecting other Michelangelo workloads.
